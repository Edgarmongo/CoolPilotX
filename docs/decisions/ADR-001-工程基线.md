## A-01 数据库选用 PostgreSQL 16

**裁定**：业务数据库使用 PostgreSQL 16，数据库名 `coolpilotx`，表统一 `cpx_` 前缀。

**理由**

1. 金额精度。本项目大量计算比率、周转天数、分期还款，PostgreSQL 的 `numeric` 是精确十进制，`numeric(18,2)` 不会像浮点那样产生 `0.1+0.2` 的尾差；MySQL 的 `DECIMAL` 同样精确，但 PG 对除法的默认行为、四舍五入函数更可预期。
2. 半结构化字段。指标的来源引用、假设、缺失输入是典型的 JSON 数组，`jsonb` 可直接建 GIN 索引并被 MyBatis 当作字符串读写，比 MySQL 的 JSON 更适合"既能查又能存"。
3. 约束表达力。`CHECK` 约束、部分索引（`WHERE status = 'open'`）、表达式索引在 PG 上成熟稳定。本项目的"未处理事项数""有效授权"这类查询高度依赖部分索引。
4. 窗口函数与聚合。月度流水汇总、账龄分桶、同环比都需要窗口函数，PG 的语义更完整。
5. 未来若要做向量检索，`pgvector` 的路径比 MySQL 生态更直接。

**代价**

- 国内云厂商托管 PG 通常比 MySQL 贵约 10%–20%。
- 团队若只熟悉 MySQL，需要适应 `RETURNING`、`ON CONFLICT`、`jsonb` 操作符。
- 本地开发需要单独装 PG（当前环境已装 16.15 客户端）。

**替代方案**

- MySQL 8：生态更普及，但 JSON 查询与部分索引能力弱一档。
- SQLite：零运维，但不支持并发写、无行级锁，不适合后续多用户。

**影响**

- Flyway 迁移脚本使用 PG 方言，不写 MySQL 兼容 SQL。
- MyBatis 的 `useGeneratedKeys`、批量插入 `ON CONFLICT` 写法需按 PG 调整。
- Docker Compose 中使用 `postgres:16-alpine`。

## A-02 金额一律使用 `numeric(18,2)`

**裁定**：所有金额字段为 `numeric(18,2)`，Java 侧映射为 `BigDecimal`，禁止 `double`/`float` 参与任何金额运算。

**理由**

- `numeric(18,2)` 支持到万亿级、两位小数，足够覆盖企业经营与融资规模。
- PostgreSQL 的 `numeric` 是精确值类型，`numeric / numeric` 的结果精度可控。
- 与 Java `BigDecimal` 语义一致，避免序列化过程中的精度损失。

**硬约束（写入代码规范）**

1. 金额字段命名统一以 `_amount` 结尾，禁止出现 `double amount`。
2. 除法一律 `divide(divisor, 6, RoundingMode.HALF_UP)`，比率再按展示精度二次舍入。
3. 比率字段存 `numeric(10,6)`，不存百分数字符串。
4. 返回前端时金额统一序列化为字符串，避免 JavaScript 的 53 位整数与浮点问题。

**代价**：`BigDecimal` 比较必须用 `compareTo`，不能用 `equals`（`1.0` 与 `1.00` 不相等）。这条要写进 code review 清单。

## A-03 主键：业务实体用 UUID，明细表用自增

**裁定**

| 类型 | 表 | 主键 |
|---|---|---|
| 业务实体 | `cpx_customer`、`cpx_financing_case`、`cpx_document`、`cpx_report` 等 | `id uuid primary key default gen_random_uuid()` |
| 高写入明细 | `cpx_bank_transaction`、`cpx_financial_statement_item`、`cpx_audit_log`、`cpx_ai_execution_log` | `id bigint generated always as identity primary key` |

**理由**

- 业务实体用 UUID：对外暴露的标识不可枚举，避免通过改 URL 参数越权猜测他人案件；未来做数据合并、离线导入时不会撞主键。
- 明细表用 `bigint identity`：单案件流水可达数万行，UUID 作为聚簇键会让 B-tree 页分裂更频繁、索引体积增大约 2–3 倍；明细表只在服务端内部引用，不存在枚举风险。
- PostgreSQL 16 无内置 `uuidv7()`，因此业务实体用 v4，牺牲时间有序性换取实现简单。若后续 PG 升级到支持 `uuidv7`，迁移成本很低。

**代价**：两套主键规则需要在 MyBatis 映射里区分对待，新人容易写错。

## A-04 枚举用 `varchar(32)` + `CHECK`

**裁定**：状态、类型等枚举字段统一 `varchar(32)`，用 `CHECK (col IN (...))` 约束取值，不使用 PostgreSQL 原生 `ENUM` 类型。

**理由**

- 原生 `ENUM` 增加取值需要 `ALTER TYPE ... ADD VALUE`，且在事务中历史上有限制，Flyway 迁移不友好。
- `varchar + CHECK` 修改约束就是一次普通 DDL，回滚容易。
- Java 侧用真正的 `enum` 类承载语义，数据库只做取值守卫。

**代价**：约束与 Java 枚举存在两处定义，需要在集成测试中加一条"枚举一致性校验"用例，防止漂移。

## A-05 时间统一 `timestamptz`，存 UTC

**裁定**

- 所有时间字段 `timestamptz`，数据库连接串设置 `TimeZone=UTC`。
- 仅在展示层按 `Asia/Shanghai` 格式化。
- 业务日期（如流水交易日、账期）用 `date`，不用时间戳。

**理由**：融资业务横跨多个期间，"2025 年度"这种期间标签绝不能被时区偏移影响。交易日是日历日期，不是时间点。

## A-06 首期明确单租户，暂不加 `tenant_id`

**裁定**：首期所有表不加 `tenant_id`。多企业隔离通过 `cpx_customer` 归属与案件级授权实现。

**理由**

- 你明确第一阶段只服务你本人。加 `tenant_id` 会让每条 SQL、每个索引、每个唯一约束都多一列，而收益为零。
- 真正的多租户不只是加个字段：还涉及数据隔离策略（共享库/独立 schema/独立库）、配额、计费、跨租户运维。现在做等于赌一个还没验证的商业模式。
- 后续加 `tenant_id` 是一次可预期的迁移：`ALTER TABLE ... ADD COLUMN tenant_id uuid`，回填默认租户，重建唯一索引。成本可控。

**代价**：如果半年内就要开放给其他顾问使用，会有一轮迁移工作量（约 1–2 人日/表 × 核心表数量）。

**需要你确认的点**：初稿写"为未来多用户、多企业、多顾问扩展预留架构"。我理解为**接口与权限模型预留，而非数据库字段预留**。如果你的意思是现在就要物理隔离，这条需要改。

## A-07 状态机自研表驱动，不引入 Spring StateMachine

**裁定**：用"状态定义 + 转换表 + 守卫函数 + 事件表"四件套自研，不引入 `spring-statemachine`。

**理由**

1. 本项目的状态机核心诉求是**可审计**与**可解释**，不是复杂的状态嵌套。Spring StateMachine 的持久化与恢复机制对"每次流转都要记录操作人、时间、原因、守卫结果"支持得并不顺手。
2. 13 个主状态 + 4 个异常状态的规模，用一张静态转换表就能表达清楚，测试也简单：遍历转换表逐条断言。
3. 自研版本可以直接把"守卫失败原因"返回给前端，告诉用户"缺哪份资料所以不能进入下一阶段"，这比框架抛出的异常友好得多。

**代价**：需要自己处理并发（乐观锁）与幂等（状态变更带期望前置状态）。这两点在 `CPX-BIZ-01` 里有具体设计。

**替代方案**：`spring-statemachine` 适合状态多、事件驱动的场景；本项目状态流转由人工动作驱动，不匹配。

## A-08 金额与指标只在 Java 计算

**裁定**：营业收入、毛利率、偿债备付率、账龄、期间汇总等一切数值，只能由 Java 的规则引擎计算并落库；LLM 的输出仅用于解释与文字组织。

**理由**：LLM 的算术不可复现。同一份数据问两次可能得到不同结果，这在需要"数字可核验"的交付物里是致命的。

**落地约束**

1. 指标表 `cpx_financial_metric` 必须记录 `formula`、`formula_version`、`data_period`、`source_refs`。
2. 报告中的每一个数字都必须带 `metric_id`，报告渲染器拒绝渲染无 `metric_id` 的数字。
3. LLM 生成的文字中如果出现数字，必须在提示词中限定"只能引用给定指标值"，并在后处理阶段做数字一致性校验：抽取文本中的数字，与给定指标集合比对，不匹配则打回重写。

## A-09 AI 只写"建议表"

**裁定**：Python AI 服务不得直接写任何业务表。它只能写 `cpx_ai_suggestion`（建议）与 `cpx_ai_execution_log`（执行记录）。业务事实由 Java 在人工确认后写入。

**理由**：这是"AI 不能直接修改核心业务数据或决定最终评估结论"的技术实现。把它做成表级隔离，而不是靠约定。

**落地约束**

- Java 侧的 `ai-gateway` 模块是唯一能调用 Python 的模块。
- 建议经人工 `ACCEPT` 后才转成业务数据，`cpx_ai_suggestion.status` 记录 `PENDING/ACCEPTED/REJECTED` 与处置人。
- 任何"AI 直接写业务表"的代码路径在架构测试中应当失败（用 ArchUnit 断言模块依赖）。

## A-10 文件二进制不落库

**裁定**：数据库只存文件元数据、SHA-256、存储键；二进制落在受控目录 `storage/documents/{customerId}/{caseId}/{documentId}/v{n}`。访问通过 `StoragePort` 接口，实现可替换为 MinIO。

**理由**：PG 的 `bytea` 存大文件会拖慢备份、撑大 WAL。融资资料常见几十 MB 的 PDF/Excel，必须外置。

**安全约束**（详见 `CPX-SEC-01`）

- 存储目录不在任何静态资源映射下，只能通过鉴权后的流式下载访问。
- 文件名重写为 `{documentId}_{sha256前8位}.{ext}`，不使用用户上传的原始文件名，防止路径穿越。
- 原始文件不可覆盖，修正后的数据作为新版本另存。

## A-11 中文检索先用 `pg_trgm`

**裁定**：知识库与全文检索首期使用 PostgreSQL 的 `pg_trgm` + GIN 索引，不引入 Milvus。

**理由**

- PG 默认没有中文分词（`zhparser`/`pg_jieba` 需编译安装）。`trgm` 做三元组模糊匹配对中文短语检索的召回可接受，且零额外组件。
- Milvus 当前容器已在运行但 19530 未对外暴露，说明环境尚未就绪；为一个还没验证价值的 RAG 引入向量库，属于过度设计。
- 接口层预留 `RetrievalPort`，当检索质量确实成为瓶颈时再换 BGE-M3 + Milvus，业务代码不变。

**代价**：语义检索能力缺失，只能做关键词/短语匹配。知识库规模超过约 5 万段落后，召回质量会明显下降。

## A-12 审计表 append-only + 按月分区

**裁定**：`cpx_audit_log` 只允许 INSERT，不提供 UPDATE/DELETE 接口；按 `occurred_at` 月度范围分区。

**理由**

- 审计的价值来自不可篡改。应用层不提供修改接口，数据库层用触发器阻止 UPDATE/DELETE。
- 融资案件审计量随时间线性增长，按月分区让归档与清理变成 `DETACH PARTITION`，而不是删百万行。

**记录范围（最小必要）**

- 登录、登出、登录失败
- 查看客户/案件详情
- 下载资料原件
- 上传、核验、退回资料
- 状态流转（含守卫结果）
- 评估结论变更
- 报告签发与交付
- 授权授予与撤销

**代价**：写入量增加。需要异步写入（先落本地队列再批量入库），否则会拖慢主流程。
