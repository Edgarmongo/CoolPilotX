## 一、产品定位

**CoolPilotX 是企业融资准备与分析系统。**

基于企业授权提供的资料，辅助整理经营情况、分析资金需求、识别资料缺口，并形成经过人工复核的融资准备报告。

| 项目 | 内容 |
|---|---|
| 首期使用者 | 系统运营者本人（单人全流程） |
| 业务模式 | 人工审核 + 软件辅助，交付的是专业服务而非软件许可 |
| 服务对象 | 有融资需求、需要把资料整理成可提交状态的中小企业 |
| 交付物 | 融资准备度评估报告（含证据链、待核实事项、补充建议） |

## 二、三条硬修正

这三条是对前一版设计的纠偏，写在这里是因为它们约束的不是某一处实现，而是整套模型的形状。

### 修正 1：融资准备度 ≠ 银行授信能力

**首期评估的是三件事**：资料准备情况、数据质量、经营信息的可核验程度。

**明确不评估**：

| 不评估的内容 | 原因 |
|---|---|
| 偿债能力 | 需要银行口径的现金流预测与压力测试模型，且结论具有授信含义 |
| 盈利能力与经营质量 | 属于投资/信贷判断，超出"准备"范畴 |
| 信用状况 | 需征信数据与历史履约记录，且需相应资质 |
| 行业前景 | 与资料准备无关 |
| 银行审批结果、通过率、获批概率 | 无法验证，且极易被误读为承诺 |

**允许存在的分析**：偿债情景测算可以作为**分析产物**存在，标注为"情景测算，非评估结论"，用于提示资金安排上的关注点。但它**不得**进入准备度评分，也不得转化为任何形式的授信判断。

**对产品的约束**：

- 准备度结论只有三档：`可进入正式资料提交准备` / `补充指定资料后再评估` / `当前信息不足`。
- 不输出 0–100 的分数。分数会制造精确性的假象，且无法说明"这个分数意味着什么"。
- 每份报告必须包含固定声明：本报告不代表授信评级、授信评分或审批意见。

### 修正 2：案件状态与分析结果必须分离

一个案件会经历多轮"补资料 → 重算 → 改报告"。用单一 `status` 字段描述全过程，必然导致两种失败：

- 字段被塞进十几个值，每个值都在表达不同维度的事情（"待复核"是流程，"报告已签发"是产物，二者可以同时成立）。
- 一旦回退，历史被覆盖。第 2 轮的分析结论在第 3 轮补资料后消失，无法解释"当时为什么这么判断"。

**因此拆成五个独立生命周期**，各自有状态机，通过 `caseId` 关联：

| 生命周期 | 回答的问题 | 状态数量 |
|---|---|---|
| 案件生命周期 | 这次服务走到哪一段 | 7 + 3 异常 |
| 分析轮次 | 第几轮分析，基于哪版数据 | 6 |
| 报告版本 | 这份报告处于什么效力状态 | 6 |
| 资料项 | 这份材料收到没有、核没核 | 6 |
| 待核实事项 | 这条疑问处理到哪一步 | 4 |

案件列表页展示的"进度"是这五个状态的**投影**，不是可写的字段。详见 `docs/business/financing-workflow.md`。

### 修正 3：证据链是底层能力，不是报告里的脚注

前一版把"数据来源"写在报告文字里（"数据来源：2025 年审计报告"）。这不够——它无法回答：

- 这句话用的是哪一版资料？资料后来被替换过吗？
- 这个数字是哪次计算产生的？用的哪版公式？
- 有没有人复核过？谁、什么时候、结论是什么？

**因此引入统一对象 `EvidenceReference`**，任何进入报告的数字与结论都必须挂载至少一条证据引用。报告渲染器**拒绝渲染**无证据的数字。

证据链覆盖五层：原始证据 → 结构化数据 → 指标计算 → 分析发现 → 人工复核与最终报告。详见 `docs/business/financing-domain-model.md` 第三章。

## 三、业务领域划分

十个知识域归并为**六个核心业务域**，外加一个横切的**证据与血缘域**（它不是第七个并列域，而是其余六域共用的底层能力）。

| # | 业务域 | 包含功能 | 核心交付 |
|---|---|---|---|
| D1 | 客户与融资需求 | 企业主体、联系人、融资需求 | 企业档案、融资案件 |
| D2 | 资料与数据管理 | 授权、文件、数据提取、质量检查 | 资料档案、数据质量清单 |
| D3 | 财务与经营分析 | 银行流水、财务报表、债务、经营数据 | 财务分析、资金分析 |
| D4 | 风险与准备度评估 | 差异分析、偿债情景、资料准备度 | 风险事项、评估结果 |
| D5 | 审核与报告 | 人工复核、报告版本、交付 | 融资准备度评估报告 |
| D6 | 平台与智能化 | 用户权限、AI 服务、知识库、审计 | 安全运行与 AI 辅助能力 |
| **E** | **证据与数据血缘**（横切） | 数据版本、证据引用、追溯查询 | 可核验的结论、可解释的历史 |

**D 与 E 的关系**：D1–D6 各自产生数据与结论，E 负责给它们盖上"可追溯"的章。E 不产生业务事实，只记录事实的来源与版本。

## 四、冻结的产品原则

以下九条为 V1.0 冻结项。

| # | 原则 | 具体含义 | 违反的典型表现 |
|---|---|---|---|
| P1 | 产品定位 | 企业融资准备与分析系统 | 对外宣传成"融资成功率提升工具" |
| P2 | 首期使用者 | 系统运营者本人 | 过早引入客户自助门户 |
| P3 | 业务模式 | 人工审核 + 软件辅助 | 让系统自动出具结论 |
| P4 | 数据原则 | 客户授权、最小必要、全程可追溯 | 无授权即解析；日志缺失 |
| P5 | 计算原则 | Java 确定性计算，AI 负责理解与解释 | 让模型算金额、做汇总 |
| P6 | 评估边界 | 不代表银行授信审批，不承诺融资结果 | 报告出现"预计可获批 300 万" |
| P7 | 报告原则 | 重要结论有数据来源、有计算口径、有人工复核 | 结论只有一句话，无出处 |
| P8 | 架构原则 | Java 模块化单体 + Python AI 服务 | 提前拆微服务 |
| P9 | 开发原则 | 先只读审计与设计，再形成任务卡，经批准后实施 | 未经批准建表、写迁移 |

**P5 的落地细节**：金额、比率、期间汇总、账龄、偿债倍数必须由 Java 计算并落库。LLM 输出中若出现数字，必须是占位符 `{{metric:CODE:PERIOD}}`，由 Java 渲染器替换；渲染器遇到裸数字直接拒绝生成报告。

**P7 的落地细节**：报告中的每个数字挂 `EvidenceReference`；每段分析结论挂至少一条证据；无证据的段落不允许进入签发版本。

## 五、首期交付范围（MVP）

| 阶段 | 交付功能 | 验收条件 | 是否含 AI |
|---|---|---|---|
| CPX-01 | 客户与案件管理 | 能登记企业、创建融资案件 | 否 |
| CPX-02 | 授权与资料管理 | 能记录授权范围、上传及管理文件版本 | 否 |
| CPX-03 | 数据提取与质量检查 | 能识别关键字段、缺失和冲突 | 否（规则提取） |
| CPX-04 | 财务与资金分析 | 能计算基础指标并追溯来源 | 否 |
| CPX-05 | 风险事项与准备度评估 | 能输出有证据支持的分析结果 | 否 |
| CPX-06 | 人工审核与报告 | 能完成报告复核、签发和交付 | 否 |

**AI Agent 不是首期交付的前置条件。** 先把确定性流程跑通，再逐步提高自动化程度。首期 AI 只出现在 CPX-03 的可选增强（文档分类、字段候选值），且失败不影响主流程。

**首期明确不做**：银行贷款产品匹配与导流、自动授信评分、自动向银行提交申请、多智能体自主决策、多租户 SaaS、完整会计核算、扫描件 OCR。

## 六、术语表（统一口径）

术语漂移是这类系统最常见的隐性成本。以下为唯一定义，文档与代码命名以本表为准。

| 术语 | 英文/代码 | 定义 | 易混淆项 |
|---|---|---|---|
| 融资准备度 | Financing Readiness | 资料齐备度、数据可核验性、口径一致性、需求清晰度的状态描述 | **不等于**授信能力评估 |
| 案件 | Financing Case | 一次融资服务请求，含需求、资料、分析、报告 | 不等于客户；一个客户可有多案件 |
| 案件生命周期 | Case Lifecycle | 案件在服务流程中的位置（受理/资料/分析/复核/交付） | 不等于分析进度 |
| 分析轮次 | Analysis Round | 基于某一数据版本的一次完整分析，含指标、发现、评估 | 不等于案件阶段；一个案件可有多轮 |
| 数据版本 | Data Version | 案件数据集的一次快照标识，资料变更即产生新版本 | 不等于报告版本 |
| 报告版本 | Report Version | 报告的一次修订，绑定一个分析轮次 | 不等于数据版本 |
| 证据引用 | Evidence Reference | 指向"哪份资料、哪一版数据、哪条规则、哪次复核"的结构化引用 | 不是报告里的文字注释 |
| 待核实事项 | Verification Item | 资料层面的疑问：差异、缺失、口径冲突、字段异常 | 不等于风险事项 |
| 风险事项 | Risk Finding | 分析层面的关注点，有等级、有证据、有建议 | 不等于待核实事项 |
| 质量检查项 | Quality Rule | 对数据本身施加的校验规则（勾稽、重复、期间连续） | 不等于待核实事项（后者面向企业澄清） |
| 资料项 | Case Material | 材料清单在具体案件上的实例，含状态与豁免 | 不等于文件（Document） |
| 就绪结论 | Readiness Outcome | 三档结论，只描述准备状态 | 不是评分，不是评级 |

**待核实事项与风险事项必须分开。** 前者问"这份资料能不能对上"，后者问"这件事对融资准备意味着什么"。混用会让报告既不敢下判断，又把事实和观点搅在一起。
